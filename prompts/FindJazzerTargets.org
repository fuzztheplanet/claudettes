#+TITLE: Jazzer Target Discovery

* Goal

Discover open-source Java/Kotlin projects that are promising targets for finding previously unknown vulnerabilities specifically through Jazzer fuzzing.

Aim for a *broad* set — around 40-50 strong targets — by casting a wide net across
many sources, then filtering hard by the quality bar below. Select and rank purely
by how likely a project is to contain a security issue that Jazzer could find; the
set does not need to be diverse. Breadth is a goal, but never a reason to lower the
bar: a genuinely-qualifying set of 35 beats a padded list of 50. Only fall short of
~50 if the qualifying pool is truly exhausted.

Only report projects that are genuinely interesting to fuzz with Jazzer.

Do NOT report projects merely because they are interesting for manual security research, CodeQL, Semgrep, native fuzzers, or other techniques.

Perform the research yourself. Inspect actual repositories and source code rather than relying only on project descriptions.

* Target Selection

Prefer Java/Kotlin projects containing security-relevant code that accepts attacker-controlled or otherwise untrusted input.

Particularly interesting examples include:

- network protocol parsers
- binary and text parsers
- serialization/deserialization
- cryptographic protocols and formats
- authentication/token processing
- URL/path/hostname processing
- archive and document formats
- expression/template languages
- stateful protocol implementations
- Java APIs exposing native parsers through JNI/JNA

A strong target should combine several of:

#+begin_example
untrusted input
+ complex processing
+ security relevance
+ practical Jazzer entry point
+ weak existing fuzzing
+ useful fuzzing oracle
#+end_example

Reject projects that do not have a realistic and useful Jazzer fuzzing entry point.

Avoid intentionally vulnerable applications, CTFs, toy projects, malware, and abandoned proof-of-concepts.

* Discovery

Search broadly and systematically. To reach ~50 qualifying targets you must sweep
several sources, not just one, and let discovery run wide before filtering. Only
include targets that clear the quality bar; never pad with projects that lack a
concrete Jazzer entry point.

Sources to sweep (use several):

- *GitHub code/topic search* — topics =parser=, =serialization=, =protocol=, =jvm=,
  =java-library=; and method-signature searches like =parse(byte[])=,
  =readFrom(InputStream)=, =decode(String)=, =fromJson=, =deserialize=, =unmarshal=.
- *Maven Central / popular-artifact rankings* — widely-depended-on parsing/format
  libraries with large downstream blast radius.
- *OSS-Fuzz project list* — mine it *both ways*: as a seed of fuzzable Java projects,
  and to find libraries NOT yet integrated (weak/absent existing fuzzing is a win).
- *Security advisories & CVE history* (GHSA, NVD) for Java/Kotlin parsers,
  deserializers, and format handlers — recurring-CVE libraries are strong signals.
- *Ecosystem families with heavy parsing surface* — Apache Commons/Tika/POI/PDFBox,
  Netty and protocol stacks, JSON/YAML/XML/CBOR/protobuf/ASN.1 libraries,
  image/media/document/archive decoders, JOSE/JWT/crypto libraries, template/
  expression engines, and Android/AOSP libraries with Java entry points.
- *Awesome-lists, research/conference references, and downstream dependents.*

These categories tend to be the most fruitful Jazzer targets — use them as search
leads to widen the candidate pool, not as quotas to balance:

- Text/binary format parsers (JSON/XML/YAML/CBOR/protobuf/ASN.1)
- Document/media/archive/image decoders (PDF/office/zip/tar/png)
- Network & wire protocols (HTTP/2, WebSocket, MQTT, DNS, TLS records)
- Serialization/deserialization frameworks
- Crypto / JOSE / JWT / certificate & token processing
- Expression/template/query languages (EL, SpEL, JEXL, CEL, JSONPath)
- URL/path/hostname/charset/encoding handling
- JNI/JNA wrappers exposing native parsers

Do not balance the set across categories and do not drop near-duplicates for
variety. Select and rank *strictly* by how likely each project is to contain a
security issue that Jazzer could find. If the strongest 50 targets are all format
parsers, report all 50 — likelihood of a Jazzer-findable bug is the only thing that
decides inclusion and order.

For each candidate investigate:

- attacker-controlled input
- concrete Java/Kotlin APIs suitable for Jazzer
- parser/protocol complexity
- security relevance
- existing Jazzer/fuzzing/OSS-Fuzz coverage
- previous security issues
- ease of constructing a Jazzer harness
- semantic fuzzing properties/oracles
- differential-testing opportunities
- project activity and downstream usage

Explicitly search for existing fuzzing before selecting a project.

* Ranking

Rank projects according to how attractive they are specifically as Jazzer targets.

Score each criterion from 0-4:

| Criterion | Weight |
|-----------+--------|
| Attacker-controlled input | 4 |
| Complexity reachable by Jazzer | 4 |
| Security impact | 5 |
| Lack of existing fuzzing | 5 |
| Jazzer harness feasibility | 5 |
| Semantic fuzzing potential | 4 |
| Differential-testing potential | 3 |
| Downstream exposure | 3 |
| Research saturation | -4 |
| Novelty | 3 |

Calculate:

#+begin_example
score =
(input * 4)
+ (complexity * 4)
+ (impact * 5)
+ (lack_of_fuzzing * 5)
+ (jazzer_feasibility * 5)
+ (semantic * 4)
+ (differential * 3)
+ (downstream * 3)
- (saturation * 4)
+ (novelty * 3)
#+end_example

Do not include a project in the final results if its interesting attack surface cannot realistically be reached and exercised with Jazzer.

* targets.org

Write a concise Org-mode research report.

Start with a single summary table ranking *all* targets (both tiers) by score:

#+begin_example
| Rank | Project | Score | Tier | Jazzer Entry Point | Main Opportunity |
#+end_example

Because the set is large, present it in two tiers so depth goes where it matters:

- *Tier 1 — deep dives (top ~15-20):* the full per-target template below.
- *Tier 2 — concise entries (remainder, down to ~50):* the compact template
  further below. Tier 2 is *shorter, not weaker* — it still requires a verified
  repository URL, a concrete Jazzer entry point, and a checked existing-fuzzing
  status.

Promote a Tier-2 target to Tier 1 if its score lands in the top group. Rank the
summary table and =targets.txt= across both tiers by score.

For every *Tier 1* target include the full template:

** PROJECT NAME

*** Repository

Canonical GitHub URL.

*** Why Jazzer?

Explain specifically why coverage-guided JVM fuzzing is appropriate for this project.

*** Jazzer Entry Points

Identify concrete Java/Kotlin classes and methods that could be fuzzed.

Prefer entry points accepting:

- =byte[]=
- =String=
- =InputStream=
- structured values constructible through =FuzzedDataProvider=

*** Fuzzing Strategy

Describe the most promising Jazzer harness.

Include useful invariants, semantic oracles, differential-testing opportunities, and relevant Jazzer bug detectors where applicable.

*** Existing Fuzzing

Describe existing Jazzer, OSS-Fuzz, property-testing, or other fuzzing infrastructure found.

*** First Experiment

Describe one concrete Jazzer harness that could be implemented immediately.

*** Score

Show the scoring breakdown and final score.

*** Confidence

HIGH, MEDIUM, or LOW.

For every *Tier 2* target, use this compact block instead (one per target):

#+begin_example

- Repo: <verified canonical GitHub URL>
- Entry point: <Class#method(inputType)> — the concrete thing Jazzer would call
- Why Jazzer / main opportunity: <one or two lines>
- Existing fuzzing: <none / OSS-Fuzz / property tests / harness found — with link>
- Score: <breakdown or total>
#+end_example

Tier-2 entries must still satisfy every quality rule below; they are condensed for
volume, not exempted from evidence.

* Repository List

Create =targets.txt= containing ONLY canonical GitHub repository URLs ordered from the most promising Jazzer target to the least promising.

Example:

#+begin_example

#+end_example

No numbering, scores, comments, or other text may appear in =targets.txt=.

* Rules

- ONLY report projects that are interesting to fuzz with Jazzer.
- Every reported project must have at least one concrete Jazzer entry point.
- Prefer code reachable directly from Java/Kotlin.
- Prefer attacker-controlled inputs reaching complex security-sensitive behavior.
- Prefer targets with weak or absent existing fuzzing.
- Prefer targets with semantic or differential-testing opportunities.
- Verify repository URLs.
- Inspect actual source code.
- Explicitly investigate existing fuzzing.
- Do not fabricate evidence.
- Mark uncertainty clearly.
- Aim for a broad set (~40-50) of qualifying targets; keep expanding discovery
  until you have that many that clear the bar, or the qualifying pool is exhausted.
- Never include a candidate lacking a concrete Jazzer entry point or a verified repo
  just to hit the count — a shorter honest list beats a padded one.
- Select and rank *strictly* by likelihood of a Jazzer-findable security issue; the
  set need not be diverse — do not spread across categories or drop near-duplicates
  for variety.
- Tier 2 entries are condensed, not lower-quality: verified repo + real entry point
  + checked existing-fuzzing status are mandatory for every target.
- Do not ask for confirmation during research.
- Actually create the output directory and both files.
- Ensure =targets.txt= exactly follows the ranking in =targets.org=.
